### o_que_bloqueia
CADEIA DE AWAITS QUE SEGURA O BOOT (em ordem, todos no mesmo caminho critico de init() antes do render loop sequer comecar):

1. `await WebGPUEngine.IsSupportedAsync` + `await gpu.initAsync()` — init de GPU. Em GPU fraca/Intel UHD pode demorar/travar (ver reference_chibata_telemetry: GPU travada na Intel UHD).
2. `await initPhysics(scene,-28)` — Havok WASM download+instanciacao.
3. `await auth.init()` — getSession() + _loadProfile() (2 round-trips Supabase). R_DE REDE NO CAMINHO CRITICO. Se a rede travar, o boot inteiro trava aqui; e tem `throw` (jogo nao roda).
4. `await import(Minimap.js)`, `await import(AssetEditorUI.js)`, `await import(MonsterVAT.js)` — 3 dynamic imports em serie.
5. `await CloudSave.loadStats()` — rede Supabase.
6. `await initItemCatalog()`.
7. `await CloudSave.loadInventory()` — rede Supabase.
   → SO DEPOIS de TUDO isso o `engine.runRenderLoop` comeca.
8. Dentro de _loadAssetsBackground TIER1: `await Promise.all(coreAnims)` = ~10 GLBs de ~7MB = ~70MB de download/parse so pra liberar o JOGAR.

O render loop (passo 27) so inicia depois dos awaits 1-7. Logo, mesmo a tela/cena 3D fica refem de auth+cloudsave+3 imports. A barra de progresso (_ssBootProgress) so comeca a mexer no passo 30 (TIER1 de assets) — antes disso a UI mostra "Iniciando engine 0%" parada durante toda a FASE 1.

## SERVER COLYSEUS

### server_startup
index.js (ESM top-level await) faz no boot, em ordem: (1) cria express + monitor + rate-limit de join; (2) new Server({WebSocketTransport com verifyClient de origin allowlist}); (3) define('lobby') e define('arena').enableRealtimeListing().filterBy(['map']); (4) await gameServer.listen(PORT) — rapido, so abre o socket; (5) await ensureBrasil1() — ESTE e o unico passo que pode demorar no boot porque faz I/O (matchMaker.query + createRoom); (6) setInterval(ensureBrasil1, 60000). NAO ha trabalho pesado de CPU/IO sincrono no boot — sem carregar GLB, sem precomputo. O proprio processo Node sobe em <1-2s. CONCLUSAO: o server Colyseus NAO e lento pra INICIAR. O custo de boot e dominado pelo ensureBrasil1 (1 query + 1 createRoom no driver de matchmaking, tipicamente LocalDriver in-memory = milissegundos; se driver Redis, depende da latencia do Redis).

### br1_criacao
ensureBrasil1(): matchMaker.query({name:'arena'}) -> procura sala com metadata.mode===OPEN_WORLD && region===BR. Se achar, retorna (idempotente). Senao matchMaker.createRoom('arena',{name:'BRASIL 1',map:cemetery,mode:OPEN_WORLD,region:BR,maxPlayers:50}) e depois remoteRoomCall(setMetadata,{region:BR}). Tem try/catch que loga '[BR1] erro' e retorna null (NAO crasha o processo). PROBLEMA 1 (race no boot duplo): a deteccao depende de metadata.mode/region, mas onCreate so faz this.setMetadata({name,map,mode,...}) — NAO grava region no metadata; region so e setado DEPOIS via remoteRoomCall(setMetadata,{region:BR}), que e um patch parcial. Em cluster com >1 processo, ou se 2 ticks de ensureBrasil1 correrem antes do region propagar pro driver, a query pode nao casar e criar BR1 DUPLICADA. PROBLEMA 2: setMetadata({region:BR}) via remoteRoomCall pode sobrescrever/parcializar metadata dependendo da versao; o ideal e ja passar region dentro do onCreate.setMetadata. Tempo de criacao: trivial (sem asset/IO pesado), milissegundos com LocalDriver.

### tick_custo
setSimulationInterval(_tick, 100) = 10Hz (NAO 20Hz; o comentario do header diz 20Hz mas o codigo usa 100ms). Em OPEN_WORLD (caso da BR1) o _tick FAZ early-return logo no topo (linha 1915-1930): loop O(players) so pra respawnar mortos + 5 checagens 'if(size>0) clear' (mobs/drops/props/fx/boss). Com 50 players e tudo vazio isso e ~50 iteracoes triviais por tick @10Hz = desprezivel (<<1ms). Nao ha UI rapida, nem barra de progresso real, nem paralelismo — a tela fica travada/preta ate tudo terminar.

(C) INTEGRACOES SEM TIMEOUT/FALLBACK AUTOMATICO. main.js:570 `await auth.init()` esta em serie e main.js:571 faz `throw e` se falhar — '[Auth] init FALHOU - jogo nao pode rodar'.
